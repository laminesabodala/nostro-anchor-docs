<Info>Operator-led sandbox: 0.2 Testnet USDC funds a 100 virtual XOF payout to synthetic Amina Diop. No real money moves. The presenter must keep the local services and tunnel running.</Info>

## Start here: which account do I use?

| Field | What it identifies | Use it for |
| --- | --- | --- |
| `account` | Sending partner’s Stellar public key | Authentication and SEP-12 customer registration |
| `receiver_id` | Beneficiary customer registered with Nostro | Choosing who receives the payout |
| Beneficiary alias | Destination account reference resolved through PI-SPI | Nostro’s off-chain payout; preconfigured for this demo |

For `account`, copy this **public** test key:

```text
GCZN3RM3P3M3NZH5OS6DHVXZIOGMTW4CIORHBVMRLSA3JASUHKSE4DKI
```

It is not a bank account number. Knowing the public key does not authorize payments: the corresponding private key must sign the authentication challenge locally. The same partner account is used when registering both customers.

## 1. Authenticate once

[GET /auth — request a challenge](/api-reference/authentication/request-an-authentication-challenge): enter the public key above in `account`. Leave optional fields empty for this demo.

Then validate and sign the returned `transaction` with the partner wallet. [POST /auth — obtain a token](/api-reference/authentication/exchange-a-signed-challenge-for-a-token) accepts that **signed transaction**, not the public key again. Copy its `token` into the Bearer field for the remaining calls. Never paste a private key into Mintlify.

**Presenter shortcut:** the configured local helper performs both API calls and signing:

```sh
node scripts/demo-payment.js --auth-only
```

Copy the token from `.local/sep10-token.txt`. Mintlify itself cannot sign a wallet challenge. This demo is presenter-assisted, not anonymous self-service.

## 2. Register sender and beneficiary

[PUT /sep12/customer — register a customer](/api-reference/customers/register-or-update-a-synthetic-customer):

1. Send the **Sender** example. Save the returned `id` as `sender_id`.
2. Send the **Receiver** example for **Amina Diop**. Save its `id` as `receiver_id`.
3. [GET /sep12/customer — check status](/api-reference/customers/read-customer-requirements-or-status) with each `id`. Continue when both are `ACCEPTED`.

Existing fixture references return the same IDs, so registration need not be repeated for every payment. Amina’s receiver record is already bound to a sandbox account alias. This API currently does not accept an arbitrary bank account number or mobile-wallet destination.

## 3. Get the final price

[POST /sep38/quote — get a firm quote](/api-reference/quotes/request-a-firm-sandbox-quote). Send the prefilled example:

| Field | Meaning | Demo value |
| --- | --- | --- |
| `sell_asset` | Currency/token you send | Stellar Testnet USDC (includes its issuer) |
| `buy_asset` | Currency the beneficiary receives | `iso4217:XOF` |
| `sell_amount` | Amount you send | `0.2` |
| `buy_delivery_method` | Current demo routing code | `PI_SPI` |
| `context` | The payment protocol using this quote | `sep31` |

Save the returned `id` as `quote_id`. Check `buy_amount` (100 XOF), fees (zero) and `expires_at`. Fund before expiry. You can go straight to this call: the optional price-discovery calls are not prerequisites for this fixed corridor.

<Note>PI-SPI is the payment rail, not the beneficiary or a wallet. `PI_SPI` is the existing sandbox route code and must currently remain in the request. The destination is the account associated with `receiver_id`. Bank-account and mobile-wallet choices should describe the recipient destination; they must only be advertised when implemented and tested.</Note>

## 4. Create the payment

[POST /sep31/transactions — create a payout](/api-reference/payments/create-a-sandbox-payout-request). Replace `sender_id`, `receiver_id` and `quote_id` with your saved values. Keep amount `0.2` and submit once. Save the returned `id` as your payment ID.

[GET /sep31/transactions/{id} — check readiness](/api-reference/payments/read-a-payout-and-its-status): wait for `pending_sender` and the returned Stellar destination and memo. Creating a payment does not transfer money.

## 5. Send Testnet USDC

On the presenter’s Mac, from the configured `anchor-demo` directory:

```sh
node scripts/demo-payment.js --fund <payment-id>
```

The helper checks the destination, issuer, amount and expiry, signs locally and funds this exact payment. It does not create another quote or payment. Preserve its saved state: rerunning resumes the same payment, and a completed payment returns its receipt without sending again.

## 6. Track completion

[GET /sep31/transactions/{id} — track the payout](/api-reference/payments/read-a-payout-and-its-status) with the same payment ID:

```text
pending_sender → pending_receiver → completed
```

`completed` means PI-SPI confirmed the virtual payout. Show `amount_in`, `amount_out`, `stellar_transaction_id`, `external_transaction_id` and `completed_at`. A Stellar hash alone does not prove the beneficiary was credited.

## Optional calls: when would you use them?

| Call | Question it answers | Needed for this demo? |
| --- | --- | --- |
| GET /sep38/info | Which currencies and delivery options are supported? | No; our corridor is already chosen |
| GET /sep38/prices | What other currencies can I receive for this send currency, and at what estimated rates? | No; useful for a currency selector |
| GET /sep38/price | For this pair and amount, approximately how much would arrive, including fees? | No; useful for a preview/calculator |
| POST /sep38/quote | What final amounts and fees can I use for a payment before expiry? | **Yes**; returns the quote ID |
| GET /sep38/quote/{quote_id} | What were the terms of my saved quote? | Optional recovery/readback |

The two estimate calls do not reserve a quote. Keep these standard Anchor Platform routes available for integrations; use the numbered path above for your first payment. [SEP-38 specification](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0038.md).

## If something goes wrong

- Expired token: repeat authentication.
- Expired quote before funding: request a new quote and create a new unfunded payment. Never duplicate an uncertain funded payment.
- Unavailable API: restore the presenter’s local services/tunnel.
- Tunnel header: use `ngrok-skip-browser-warning: 1` (prefilled).

The rate is illustrative (500 XOF per USDC). Testnet USDC and virtual XOF are separate transfers; the XOF comes from a prefunded simulator account. This is not real FX conversion or atomic settlement.
